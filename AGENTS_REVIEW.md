> *"Code quality is more important than development speed. Readability is more important than cleverness. Every implementation should be suitable for a public GitHub portfolio."*

**Verdict:** Strongly agree. These are the correct professional values. No changes needed.

### 1.2 KISS, YAGNI, PSR-12, Symfony Best Practices (lines 32–47)

> *"When multiple solutions exist, always prefer: simplicity, readability, maintainability, consistency."*  
> *"Follow: KISS, YAGNI, PSR-12, Symfony Best Practices."*  
> *"Avoid: overengineering, unnecessary abstractions, unnecessary complexity, clever code."*

**Verdict:** Core principles are spot-on. The tension between "KISS" and "production-quality" is healthy — it forces the engineer to justify every abstraction. No changes needed.

### 1.3 Thin controllers, business logic in services (lines 62–79)

> *"Keep controllers thin. Repositories contain only database logic. Business logic belongs in services."*

**Verdict:** This is the canonical Symfony layering. It's the right default for the project size. No changes needed.

### 1.4 Approval-gated workflow (lines 88–104)

> *"Before writing any code: explain what, why, list files, wait for approval."*  
> *"After implementation: summarize, explain decisions, list files, suggest commit message."*  
> *"Never continue without user approval."*

**Verdict:** Excellent guardrail for an AI-assisted workflow on a learning project. No changes needed.

## 2. Rules That Are Unclear or Ambiguous

### 2.1 "Write code that a Junior PHP developer can understand" (line 55)

**Problem:** Subjective and unmeasurable. What a junior understands varies wildly. Does this mean:
- No generics/templates?
- No PHP 8.4 property hooks?
- No match expressions?
- No first-class callables?
- No backed enums?

**Recommendation:** Replace with measurable criteria. For example:

> *"Prefer explicit, descriptive variable and method names. Avoid PHP features that require reading documentation to understand at a glance (e.g., complex reflection, closures with `bindTo`, deeply nested ternaries). PHP 8.4 language features are acceptable when they improve clarity."*

### 2.2 "Business logic belongs in services" (line 79)

**Problem:** "Business logic" is undefined. Where does input transformation logic go? Where does authorization logic go? Are DTOs "business logic" or "application logic"?

**Recommendation:** Clarify with concrete examples:

> *"Business logic (e.g., 'a completed task cannot be edited', 'priority must be medium or higher for overdue tasks') belongs in service classes under `src/`. Application logic (e.g., request parsing, response formatting, form handling) belongs in controllers and form types."*

### 2.3 "Use standard Symfony architecture" (line 60)

**Problem:** Assumes the reader knows what "standard Symfony architecture" means concretely. The `IMPLEMENTATION_PLAN.md` in this repo proposes `src/Domain/Repository/` interfaces, `src/Application/` services, and `src/Dto/` — which is already a layered approach beyond "standard".

**Recommendation:** Define the allowed layers explicitly:

> *"Allowed layers: Controller, Form, Service, Repository, Entity. Additional layers (DTO, EventListener, Security) are permitted when they solve a concrete, demonstrable problem. New directories under `src/` must be justified in implementation notes."*

## 3. Important Engineering Rules That Are Missing

### 3.1 Testing (CRITICAL)

There is no rule about testing whatsoever, yet the project goal states "production-quality." Production-quality without tests is a contradiction.

**Recommendation:** Add a `## Testing` section:

```markdown
## Testing

- Every controller action must have at least one functional test.
- Every repository method not auto-generated by Doctrine must have a test.
- Before merging a feature, run `php bin/phpunit` and fix all failures.
- Use `dama/doctrine-test-bundle` for test database isolation (already in plan).
- Tests go in `tests/Functional/` with the same namespace structure as the tested code.
- Test database uses `APP_ENV=test` with a separate database.
```

### 3.2 Doctrine Best Practices

No rules govern how entities should be designed beyond "in `src/Entity/`."

**Recommendation:** Add:

```markdown
## Doctrine

- Always use attribute mapping (`#[ORM\Entity]`, `#[ORM\Column]`), never XML or YAML.
- Use `#[ORM\HasLifecycleCallbacks]` with `#[PrePersist]`/`#[PreUpdate]` for timestamps.
- Avoid bidirectional relationships unless required by a specific feature.
- Eager loading (`fetch: 'EAGER'`) is forbidden — use query builder `->addSelect()` or DQL joins instead.
- Repository methods must not return `null` when the caller expects an entity; throw a domain exception instead.
- All database changes must go through migrations. Never modify the schema manually.
- Migration names follow the pattern: `VersionYYYYMMDDHHMMSS.php`.
```

### 3.3 Security

No mention of CSRF, input escaping, SQL injection prevention, or access control patterns.

**Recommendation:** Add:

```markdown
## Security

- All routes that mutate data (POST, PUT, PATCH, DELETE) must have CSRF protection (implicit via Symfony forms) or use API tokens.
- All user input rendered in Twig templates is auto-escaped — never use `|raw` without explicit architect approval.
- Use `#[IsGranted]` attribute on controller classes or methods, not manual checks in controller bodies.
- Voter classes are preferred over inline `$this->isGranted()` for complex authorization logic.
- `APP_SECRET` must never be committed to the repository (already in `.gitignore` via `.env.local`).
```

### 3.4 Code Style and Static Analysis

PSR-12 is mentioned but no enforcement mechanism is specified.

**Recommendation:** Add:

```markdown
## Code Style

- Every commit must pass `vendor/bin/php-cs-fixer fix --dry-run --diff` with zero changes.
- Use `@PSR12` and `@Symfony` rulesets.
- Strict types (`declare(strict_types=1)`) in every PHP file.
- PHPStan level 6 minimum; level 8 target for `src/Entity/` and `src/Service/`.
```

### 3.5 Naming Conventions

No rules for naming controllers, routes, services, or methods.

**Recommendation:** Add:

```markdown
## Naming

- Controllers: singular noun, `Controller` suffix (`TaskController`, not `TasksController`).
- Route names: lowercase, dot-separated (`app_task_create`, not `app.task.create` or `taskCreate`).
- Service methods: verb-first (`createTask`, not `taskCreate`).
- Form types: entity name + `Type` suffix (`TaskType`).
- Repository methods: `find` prefix for queries returning entities, `get` prefix for queries returning scalar/aggregate.
```

### 3.6 Dependency Injection

No guidance on DI patterns.

**Recommendation:** Add:

```markdown
## Dependency Injection

- Always use constructor injection. Never use setter injection or service location.
- Dependencies must be declared as interfaces (from `src/Domain/Repository/`) in service constructors, not concrete classes.
- Do not inject the container (`Psr\Container\ContainerInterface`) into any class except `Kernel.php`.
```

### 3.7 API Design (REST)

The IMPLEMENTATION_PLAN.md includes REST API, but AGENTS.md has no rules for it.

**Recommendation:** Add:

```markdown
## API

- All API routes are prefixed with `/api` and return `application/json`.
- Use HTTP status codes consistently: 200 (OK), 201 (Created), 204 (No Content), 400 (Bad Request), 401 (Unauthorized), 403 (Forbidden), 404 (Not Found), 422 (Unprocessable Entity), 500 (Internal Server Error).
- Validation errors return `{"errors": {"field": "message"}}`.
- Serialization uses Symfony Serializer with attribute groups (`task:read`, `task:write`).
- Never expose Doctrine entities directly in JSON responses without serialization groups.
```

### 3.8 Environment and Secrets

**Recommendation:** Add:

```markdown
## Environment

- `.env` contains defaults only — all real values go in `.env.local` (gitignored).
- Production secrets use `config/secrets/prod/` (encrypted, committed) + `prod.decrypt.private.php` (never committed).
- Never log or dump environment variables containing secrets.
- `APP_ENV` values: `dev`, `test`, `prod` only (matches `Kernel::getAllowedEnvs()`).
```

### 3.9 Git Practices

The workflow section mandates suggested commit messages but no format standard.

**Recommendation:** Add:

```markdown
## Git

- Commit messages follow Conventional Commits: `type(scope): description` (e.g., `feat(task): add CRUD controller`).
- Types: `feat`, `fix`, `test`, `docs`, `chore`, `refactor`.
- One logical change per commit.
- Never commit `var/`, `vendor/`, `.env.local`, or IDE files.
```

## 5. Rules That Conflict With Symfony Best Practices

### 5.1 Blanket ban on Clean Architecture patterns (lines 81–82)

> *"Do not introduce Clean Architecture, DDD, CQRS, Event Sourcing, or other advanced patterns unless explicitly approved."*

**Problem:** This is too aggressive. Symfony Best Practices themselves recommend patterns that overlap with "Clean Architecture lite":

- **Repository interfaces**: Symfony's own documentation shows `src/Repository/` implementations implementing a custom `UserRepositoryInterface`. The IMPLEMENTATION_PLAN.md correctly proposes this.
- **DTOs**: The Symfony Form component works best with data transfer objects. Banning "clean architecture" could be read as banning DTOs.
- **Service layer**: Symfony Best Practices explicitly recommend "services" for business logic. This rule already allows that, but the blanket ban on "advanced patterns" creates ambiguity about whether a `TaskService` with a `TaskInput` DTO is "clean architecture" or "standard Symfony."

The IMPLEMENTATION_PLAN.md already proposes `src/Domain/Repository/` interfaces, `src/Dto/`, and `src/Application/` services — this rule as written would block that.

**Recommendation:** Replace with a precise scope:

```markdown
## Allowed and Forbidden Patterns

**Allowed (use freely):**
- Repository interfaces for testability (`src/Domain/Repository/` + `src/Repository/`)
- Service layer for business logic (`src/Application/`)
- DTOs for API input/output and form data (`src/Dto/`)
- Custom exceptions for domain errors (`src/Domain/Exception/`)
- Symfony Event subscribers/listeners (`src/EventListener/`)

**Forbidden (requires explicit architect approval):**
- CQRS (separate read/write models)
- Event Sourcing
- Full Domain-Driven Design with aggregates, value objects, and bounded contexts
- Hexagonal/ports-and-adapters architecture (separate adapter directories)
- Custom framework abstractions (e.g., wrapping Doctrine EntityManager in a custom class)
```

### 5.2 No mention of Form component for validation (lines 62–79)

> *The architecture flow is: Controller → Service → Repository → Entity*

**Problem:** This flow omits the Symfony Form component entirely, yet forms are the recommended way to handle user input, validation, and CSRF. Symfony Best Practices state that form types should handle input transformation and validation.

**Recommendation:** Update the architecture flow:

```
Controller
   ↓
Form (input validation + transformation)
   ↓
Service (business logic)
   ↓
Repository (persistence)
   ↓
Entity (data model)
```

And add:

> *"Use Symfony Form types for all user-facing data entry. Forms handle validation and CSRF protection. Controllers delegate to forms, not directly to services, when receiving user input."*

## 7. Final Assessment

The AGENTS.md is a solid foundation. The core values (quality, simplicity, readability, approval-gated workflow) are correct and should not change. The architectural philosophy (thin controllers, service layer, standard Symfony) is the right default for this project size.

The two critical gaps are:

1. **No testing rules** — this undermines the "production-quality" goal.
2. **The architecture rule is too restrictive** — as written, it blocks repository interfaces and DTOs, which are reasonable and testable patterns that already exist in the approved IMPLEMENTATION_PLAN.md. This creates an immediate conflict that must be resolved before implementation begins.

The IMPLEMENTATION_PLAN.md should also be updated to align with the clarified architecture rules once this review is addressed — specifically, the `src/Domain/` and `src/Application/` directories either need explicit blessing in AGENTS.md, or the plan should be simplified to flat `src/Service/` and `src/Dto/`.
